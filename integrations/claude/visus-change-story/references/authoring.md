# Shared authoring contract

Run from the Git worktree root, or pass `--root <worktree>` on each command. Draft and input-file paths resolve relative to that root. Use the workflow's selected base. The CLI needs no server or MCP configuration.

1. Run `visus prepare --draft .visus/draft-01.json`, adding `--base <ref>` when selected. Choose an unused filename; preparation refuses overwrites. Preserve its `updateId`, `sourceId`, and `expectedRevision`. Page remaining units with `--offset N --limit N` without `--draft`, keeping the same base. If `sourceId` or `expectedRevision` changes between pages, prepare again before authoring.
2. Inspect the changed code and relevant callers. Use only returned change-unit IDs as refs. Edit `stories`, optional `entities`, and optional `exclusions`; read [the example](example.md) only if needed, or run `visus schema` for the full contract. Group changes by outcome, with readable titles, summaries, entity labels, and supported relationship explanations. Keep stable story IDs. Do not invent intent, alternatives, effects, or test success; say when intent is unknown. Mark test changes with group kind `tests`, distinguishing test purpose from executions actually observed.
3. Account for every unit in a story's `groups[].refs` or an exclusion with a specific reason. Entity, decision, and impact refs alone do not count toward coverage. Impact endpoints must name existing entities; distinguish direct from inferred effects. An empty comparison can use `stories: []`.
4. Updates replace complete records with matching IDs and retain unrelated records whose references remain valid. Use `removeStories` / `removeEntities` for explicit removal. Omit `exclusions` to retain valid exclusions; providing it replaces the list.
5. Run `visus validate --file .visus/draft-01.json`, then `visus publish --file .visus/draft-01.json`. Invalid input, stale source, or revision conflicts require repair. For stale source/revision, prepare a new draft and remap the explanations to current refs. A valid partial update reports `incomplete` and can be published incrementally. An unchanged retry returns its saved acknowledgment; modifying an already-published draft requires a new generated update ID. Even duplicate validation/publication does not recheck freshness.
6. Run `visus check`. Only `fresh` means a published, current, fully accounted review; `missing`, `stale`, and `incomplete` exit nonzero. Repair pending/stale units before claiming completion, respecting the hook's retry boundary when applicable. Report the draft path, scope, revision, and actual check status.

Published JSON lives at `.visus/reviews/<scope>/revisions/<revision>.json`; an existing legacy store can use `.diff-vis/` instead. Editing a draft does not update the viewer until publication. Keep reports and captured evidence local and untracked. If a portable bundle is requested, use `visus export --scope <scope> --revision <revision> --out <directory>`; exports include source evidence and are not sanitized.

For a tools-only agent, read [MCP authoring](mcp.md) instead of attempting shell/file commands.
